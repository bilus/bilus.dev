While porting [Phoenix LiveView to
Go](https://blog.bilus.dev/posts/porting-liveview-to-go/), I went down the
rabbit hole of researching different ways to generate Go code. I've tried
jennifer, dave/dst, and a couple of other ways. Finally, I settled on a really
cool approach I extracted into a library. [qudy](https://github.com/bilus/qudy)
made the code generation parts very readable.

Here's a simple stringer. It generates a `String()` method for an enum:

```go
func main() {
	pkg := flag.String("package", "main", "the package of the generated file")
	typ := flag.String("type", "", "the enum type")
	flag.Parse()
	if *typ == "" || flag.NArg() == 0 {
		fmt.Fprintln(os.Stderr, "usage: stringer [-package name] -type T constant...")
		os.Exit(2)
	}
	writeStringer(*pkg, *typ, flag.Args())
}

// writeStringer writes an enum's String method and its guard against changed constants.
func writeStringer(pkg, typ string, names []string) {
	//`// Code generated by the qudy stringer example. DO NOT EDIT.
	//`
	//`package ~pkg
	//`
	//`import "fmt"
	//`
	//`func (v# ~typ) String() string {
	//`	switch v# {
	for _, name := range names {
		//`	case ~name:
		//`		return "~name"
	}
	//`	}
	//`	return fmt.Sprintf("~typ(%d)", v#)
	//`}
	//`
	//`func _() {
	//`	// An "invalid array index" error means that a constant's value changed.
	//`	var x# [1]struct{}
	for i, name := range names {
		//`	_ = x#[~name-~i]
	}
	//`}
}
```

And so, a Lisp-to-Go transpiler was born, in < 500 lines of code. I illustrated

Ideas coming out of ideas coming out of ideas. /Daddy joke

The compiler parses a small Lisp dialect and produces Go source. You compile that
source with Go, which checks the types and lets you use the rich library
ecosystem.

## Why Lisp?

Frankly, Lisp is easy to parse. And I happen to love Clojure.

So what's Lisp like? It's all *parentheses*. In Go, you write:

```go
1 + 2
```

In Lisp, the operator comes first:

```clojure
(+ 1 2)
```

To call a function, put its name first too: Go’s `f(a, b)` becomes `(f a b)`. To
nest an expression, put another expression where an argument would go:

```clojure
(+ 1 (* 2 3))
```

The particular syntax I borrowed comes from Clojure, a modern Lisp best known
for running on the JVM. This is a toy Clojure-like language with Go types;
existing Clojure programs won’t run unchanged.

## Writing the output

Before parsing Lisp, let’s look at how we produce Go. A generator can write
source with ordinary printing calls:

```go
name := "square"
fmt.Printf("func %s(n int64) int64 {\n", name)
fmt.Println("    return n * n")
fmt.Println("}")
```

With Qudy, I write:

```go
name := "square"
//`func ~name(n int64) int64 {
//`    return n * n
//`}
```

The comments beginning with a backtick describe output lines. Qudy copies most
of their contents literally; `~name` inserts the value of the Go variable
`name`. Both versions produce:

```go
func square(n int64) int64 {
    return n * n
}
```

Qudy turns those comments into emit calls which by default write to standard
output. The surrounding code stays ordinary Go, so loops, conditions, and helper
functions work as usual. I can read the generated function’s shape without
mentally removing quotes and escape sequences.

Qudy can do more, but to follow the examples below you need
just two more bits of its notation. `~{expression}` inserts the value of a Go
expression, such as a helper call. A trailing backslash suppresses the newline,
letting several helpers contribute to one line.

Two programs generate code here. First, Qudy processes the compiler template and
produces a Go program. Then that program parses Lisp and writes Go. The Lisp
program never sees Qudy. Matryoshkas.

## Parsing an expression

Back to `(+ 1 (* 2 3))`. Before generating anything, we need to separate its
operation from its arguments.

The parser represents each piece of source as a *form*. A form can be an
individual item, like `+` or `1`, or a collection containing other forms. Here
is the relevant part of its Go representation, with type hints and source
positions omitted:

```go
type form struct {
    atom  string
    delim rune
    kids  []form
}
```

`atom` holds the text of an individual item. A collection instead records its
opening delimiter and its children. Parsing `(+ 1 2)` gives us:

```go
form{
    delim: '(',
    kids: []form{
        {atom: "+"},
        {atom: "1"},
        {atom: "2"},
    },
}
```

For `(+ 1 (* 2 3))`, the last child is another collection, containing `*`, `2`, and `3`.

I use Go’s `text/scanner` package to split the input into tokens: parentheses,
names, literals, and so on. After the parser encounters an opening parenthesis,
its main loop is:

```go
for t = s.Scan(); t != close; t = s.Scan() {
    f.kids = append(f.kids, read(s, t))
}
```

This excerpt leaves out comment handling. `close` is the expected closing
delimiter. `read` returns a single item directly, or runs this same loop when it
encounters another opening delimiter. By calling itself recursively, `read`
handles nested collections. The full parser also checks for unexpected closing
delimiters and premature end of input.

At this point, the parser hasn’t decided whether a collection means addition, a
function call, or a function definition. It has only recorded what was written
and how it was nested.

## Giving the forms meaning

The generator decides by looking at the first item. In `(+ 1 2)`, that item is
`+`, and the remaining items are operands.

For arithmetic, we write an opening parenthesis, generate the operands with the
operator between them, and write a closing parenthesis. This is the central part
of the operator helper:

```go
//`(\
for i, a := range args {
    if i > 0 {
        //` ~op \
    }
    expr(a, want)
}
//`)\
```

`op` is the Go operator and `args` holds the operand forms. `expr` generates an
expression; `want` passes along a known result type when one is available. The
surrounding code checks the operand count and translates operators whose Go
spelling differs.

For `(+ 1 2)`, the loop generates `1`, writes ` + `, then generates `2`. Integer
literals explicitly become `int64` values, so the output is:

```go
(int64(1) + int64(2))
```

For a nested operand, `expr` calls the operator helper again. Our larger
expression becomes:

```go
(int64(1) + (int64(2) * int64(3)))
```

Each helper call closes the parentheses it opened. Each helper produces a
complete piece of syntax, which makes the generation code much easier to follow.

## Put it in a function

An expression needs somewhere to live. Here’s a function in our Lisp:

```clojure
(defn square ^int64 [^int64 n]
  (* n n))
```

`defn` introduces a named function. The square brackets contain its parameters.
`^int64 n` gives `n` its type, and the hint before the parameter vector gives
the function its result type. The last expression in the body supplies the
result.

The generator already knows how to handle `(* n n)`. It just needs to wrap that
expression in a function. After validating the form, the `defn` case does this:

```go
name, result := ident(args[0]), args[1].hint
//`func ~name(~{parameters(args[1])}) ~result {
body(args[2:], result)
//`}
```

`parameters` returns the parameter declarations as text. `body` generates the
body and adds `return` before its last expression when the function has a
result. The template owns both parentheses and both braces. The output, after
formatting, is:

```go
func square(n int64) int64 {
    return (n * n)
}
```

To call it, add a package, an import, and `main`:

```clojure
(package main)
(import "fmt")

(defn square ^int64 [^int64 n]
  (* n n))

(defn main []
  (fmt.Println (square 12)))
```

Save that as `square.lisp` in the repository’s `examples/lispg` directory. From there:

```sh
go run . square.lisp > /tmp/square.go &&
  gofmt -w /tmp/square.go &&
  go run /tmp/square.go
# 144
```

The resulting Go program:

```go
package main

import "fmt"

func square(n int64) int64 {
	return (n * n)
}
func main() {
	fmt.Println(square(int64(12)))
}
// ... helper functions
```

## How far does it go?

The [full example](https://github.com/bilus/qudy/tree/master/examples/lispg)
also supports local bindings, conditionals, closures, and homogeneous lists. Its
Lisp examples implement recursive `map`, `reduce`, and `filter`, print a
directory tree, and run a small HTTP server:

```clojure
(package main)
(import "fmt" "log" "net/http")

(defn main []
  (http.HandleFunc
   "/"
   (fn [^http.ResponseWriter w ^*http.Request r]
       (fmt.Fprintf w "Hello, %s\n" r.URL.Path)))

  (log.Fatal
   (http.ListenAndServe ":8080" nil)))
```

Doesn't do much, does it.

Anyway, it's a toy language. Go is verbose and this baby is just 500 lines of
it.
